# SPEED の録画でバランスを分析する

問いと目標 → 指標 → 仮説 → 少数の調整候補 → 条件を揃えた前後比較 → 次の試遊、を繰り返す。感想は分析課題の発見と体験評価に使い、観測データと併せて判断する。

対象はリポジトリの `speed/` にある本番 Godot。`demo/` と実験場の記録は別の母集団として扱う。録画は観測データであり、入力を再生できるリプレイとして扱わない。

## 調整モードと担当範囲

分析の最初に、調整モード・目的・対象ステージ・変更候補の範囲を明示する。ステージ番号や利用者名だけで担当を推定しない。

| モード | 調整候補に含める範囲 |
|---|---|
| 基礎調整 | ステージ4等の試遊を基準に、依頼で合意されたゲーム共通のXP量・成長曲線・機体強化幅等と対象ステージの値を分析する。共通値の候補には他ステージへの影響と基準の版を添える |
| ステージ制作 | 基礎担当が調整した共通値を固定条件として、担当ステージ固有の配置・出現・攻撃設定等を分析する。共通の敵種定義・共通設定・基礎システムへの変更を通常の調整候補に含めない |

担当やモードが不明なら、共通値変更を勧める前に確認する。その間も観測の整理と確認済みのステージ固有範囲の分析は進められる。

ステージ固有値かどうかは、保存先だけでなく参照先と適用経路で確認する。再登場敵のHP・攻撃力・射程・攻撃間隔を調整したい場合は、既存のステージ別上書きがその値に対応するかを実装で確かめる。共有Enemy Resourceの編集を、そのステージだけの変更として提案しない。上書きの仕組みがなければ、基礎側への相談事項として「対象ステージ/敵/時刻・観測と感想・必要な局所変化・現行の制約・波及する参照先・確認してほしい判断」を短く示す。分離方法の追加は未決の設計相談として扱い、実装済みの仕組みや確定仕様にしない。

## 入口と入力

1. リポジトリルートの `AGENTS.md`、`docs/README.md`、[制作ガイド](../../../docs/dev/stage-production.md)、[AI向け制作参照](../../../docs/dev/stage-production-ai.md)を読む。記録形式と開始条件の正本は[設計書14.3](../../../docs/architecture.md#143-プレイの記録)。対象ステージの仕様と到達目標も確認する。
2. 利用者から録画ファイル（複数可）またはディレクトリ、調整したい体験、該当時刻の感想を受け取る。相対パスは依頼で指定された基準から解決し、基準がなければリポジトリルートを使う。感想がなければ数値の分析を進め、体感との対応は未確認とする。
3. 保存先が不明なら `speed/scripts/dev/play_recorder.gd` の `folder()` を読む。OS の書類フォルダ内 `SPEED/recordings/`、書類フォルダを取得できない場合はプロジェクトの `user://recordings/` を探す。書類フォルダのリダイレクトや Godot のユーザーデータ設定を考慮し、OS ごとの固定絶対パスを仮定しない。利用者が既にゲームを開いていれば、録画待機中の F10 でも場所を確認できる。分析のためにゲームを勝手に起動しない。
4. 最初はヘッダー・末尾・型別件数を確認し、目的に合う少数の録画を詳しく読む。JSONL は Python 標準ライブラリ等で行ごとに解析できる。録画本文を大量に会話へ貼らず、入力を読み取り専用で扱う。解析中のエラーもファイル名と行番号で報告する。

[計測の読み方](references/measurement.md)を開き、目的に必要な限界と計算を確認する。形式を解釈するときは現行の recorder とイベント発生元を照合する。文書のパスが改修で古くなった場合は `rg` で現実の呼び出し先を探し、差を報告する。

## 0. 調整基準を確認し、不足する基準づくりを支援する

[制作ガイドの成長配分](../../../docs/dev/stage-production.md#3-フェーズの狙いを配置にする)に沿って、対象ステージの仕様と会話で既に合意した目標を先に読む。ステージ4なら[成長目標の正本](../../../docs/game/stages/stage-4.md#2-フェーズと成長目標)を参照する。具体的な目標値はこのスキルへ複製しない。

- **既存の基準を使う。** 時刻ごとの到達レベル、選択間隔、ボス前の装備完成度、想定する機体強化を、確定・仮目標・未決に分けて整理する。仮目標も比較基準として使い、記載済み・合意済みの内容を再質問しない。会話と文書が食い違う場合は根拠と差を示す。
- **今回必要な不足だけ相談する。** 未設定の基準が判断を妨げる場合は、まずボス前に求める装備完成度、そのためのフェーズ別選択回数・間隔、累計の時刻別目標レベルの順に不足を確認する。必要な項目を一つずつ相談し、全目標を一律に必須としない。選択肢と意味を説明しても、AIが目標数値や許容幅を勝手に確定しない。
- **未決でも観測は進める。** 基準がない箇所は実測値を整理し、適否や最適値の判断を保留する。採用する目標は利用者が決め、記録先は文書規定に従う。目標設定の相談だけで仕様書や設定を編集しない。
- **レベルと強さを別々に見る。** [共通の成長仕様](../../../docs/spec.md#9-成長)に照らし、レベル到達、実際のカード選択、武器・特性の段と完成度、機体強化・実効能力値を別軸で扱う。レベルだけから攻撃力・最大HP等が増えたと解釈しない。

比較結果は「時刻/フェーズ・目標と状態（仮/確定/未決）・実測レベル/到達秒・目標との差・選択間隔・装備完成度・感想」を必要な列だけ使って示す。目標へ届かない原因は、倒せる数・XP供給・回収・必要XP・選択の保留等に分け、目標値を実測値に合わせて無断で動かさない。

## 1. データ適格性を確認する

ファイルごとに、形式版・実在する項目・開始条件・観測範囲・終了状態・実行条件を短く一覧にする。現行の出力は `schema_version=4`・`measurement_version=1`。同じ schema 4 でも追加計測のない録画があるため、測定版と `conditions`・`loadout`・`hurt`・XPイベント等の実在を確認する。欠落を0や未発生へ置き換えず、未対応版は目的に使える項目だけで分析する。録画日時やファイル名だけで版や通常開始を決めない。

開始条件の判定は設計書の区分を使う。通常成長の候補は次のすべてを満たすものに限る。

- `run_start.source` が `stage_start` または `stage_launcher`。
- `run_start.t=0`、`recording_start.t=0`。
- `recording_start.trigger=armed_before_run`、`missing_prefix=false`。

目的に必要な初期HP・XP・装備・機体強化・モードも比較する。`timeline` は時刻0でも区間検証、`during_run` / `missing_prefix=true` は前半欠落、旧形式・欠けた開始条件・`unknown` は出自不明として通常成長の集計から既定で除外する。途中時刻から XP0 で始めたランを通常プレイへ混ぜない。除外は目的ごとに行い、使える区間の性能・挙動まで捨てない。

終了状態は開始条件と別に持つ。`clear`・`death`、`stopped`・`quit`、`end` 欠落を区別する。終了未確認を死亡やクリア失敗へ置き換えない。JSON破損、複数の `start`、逆行する時計、不自然な集計間隔は該当行を示す。壊れた行を飛ばして連続したランに見せず、信頼できる観測範囲を限定する。時計の停止はボーナスやカード選択でも起きるので、間隔だけで欠落と断定しない。連番やチェックサムがなく、構文的に正常な中間行の欠落を完全には検出できないことも示す。

異なるファイルを同じランと推定して連結しない。F9 停止・再開は別ファイルになり、共通のランIDや連続性を保証する情報がない。別名コピーも内容ハッシュで確認し、二重に数えない。

`run_start.conditions`・`recording_start.conditions` の設定・強化・能力値・乱数と、初期化時の `conditions.identity` のコード/データ/実効値ハッシュを照合する。`build_revision` が空なら実行コミットは不明のまま残す。`stage_file_sha256_at_start` は実際のステージリソースだけのハッシュであり、改修後は `.content/` のRuntimeStageを指す。編集元 `.tres` のハッシュと無条件に比較せず、依存全体の一致にも使わない。`engine_version` はゲームのコミットではない。ディスク内容・読み込み済み資源・途中の変更を区別し、詳細は参照文書に従う。分析時の `git rev-parse HEAD` と `git status --short` は分析側の状態として示し、実行時の状態へ転用しない。

## 2. 時間帯・観測できるビルド別に集計する

- 記録内の `bands`・`band` を使い、同じステージ・実行条件・開始区分で分ける。現データの時間帯境界を過去の録画へ当てはめない。
- 成長は `levelup` の到達秒、選択機会と `pick` の選択秒、XP供給・取得・残存を対応づける。レベルアップと実際の選択には遅れや複数レベルの保留がある。
- ビルドは `recording_start` の装備と `loadout.previous/current` の差分から追い、`end` の最終装備と照合する。初期選択・おまけ・彗星取得/交換・直接変更・解除の経路を区別し、`pick` は選択の観測として読む。`loadout` がない旧録画や差分が欠ける区間では正確な装備を補完せず、「選択履歴」「最終ビルドによる群分け」までに留める。
- `sample` のXP・撃破・与被ダメージは前回 sample（最初は録画開始）以降の区間値として合算する。敵数・HP・残存XPは時点値として扱い、足し合わせない。初期累計や `end.kills` を区間合計へ重ねない。
- 敵のライブ調整は開始時の `conditions.enemy_tuning` と `enemy_tuning_changed.values` で設定区間を分ける。適用時刻は `event_t/event_world_t` を使い、通知時刻との違い、保存通知との違いを保つ。
- 区間が時間帯・装備変更・ボーナス・設定変更の境界を跨ぐ場合は「境界混在」とする。3秒区間の数を境界の前後へ正確に分割しない。最終 sample は短いことがあり、常に3で割らず観測時間を使う。
- `t`（ラン秒）、`real_t`（録画開始後の実秒）、`world_t`（世界秒）を使い分ける。ボーナス中は `t` が進まなくてもXPや戦闘が進む。0秒区間の成長率・DPSを作らず、ボーナスを分けるか、境界混在の量として示す。

比較母集団は条件の近い複数ランとし、時間帯・ビルド・共通設定版・開始条件で層別する。集計・推論の単位はランとし、3秒sampleや同一ラン内の敵を独立標本として件数を増やさない。プレイヤーや試遊順による違いも残す。

各ランの値・観測範囲から、平均に加えて中央値・分位点や分布・ばらつき・ラン数を、問いに必要な範囲で示す。少数ランでも記述統計を出し、不確実性を添える。死亡・途中終了による打ち切りと完走者だけの偏りを明記し、詳しい比較方法は[複数ランの比較](references/measurement.md#複数ランの比較と不確実性)を使う。

## 3. 観測と仮説を分ける

調整目的に必要な指標を[計測の読み方](references/measurement.md)から選ぶ。全指標を必須にはしない。

- **観測**：ファイル名、行番号または秒範囲、分母、単位を添える。集計値には計算方法と欠測範囲を添える。
- **実装からの計算**：参照したファイル・条件を示す。現在の設定による計算を過去ランの実測値へ置き換えない。
- **仮説**：観測を説明できる原因と、競合する説明を分ける。相関や同時発生を因果と断定しない。イベントが保存されていないことを「発生しなかった」の根拠にしない。

依頼の結論を妨げる不足だけを優先順に挙げる。「何の判断ができないか」「追加で最小限何を記録・確認すればよいか」を対応づける。記録項目の追加は提案に留める。

## 4. 感想と併せて調整候補を示す

該当する時間帯の感想（例：硬い、暇、避けづらい、育たない）を観測に対応づける。感想を記録から創作しない。仕様上の目標、仮目標、未決の目標を区別する。

影響の大きい候補を少数に絞り、対象ファイル・項目、確認できた現在値→候補値、狙う体験、根拠、反証する再試遊条件を示す。実行時の設定や因果が不明なら方向と確認手順までに留め、精密な数値を捏造しない。各候補にステージ固有/共通の区分と適用範囲を添え、上の調整モードに収まることを確認する。共通値の変更は基礎調整で合意した範囲だけを候補にし、ステージ制作では基礎側への相談に分ける。

## 5. 変更前後を比較する

合意された変更後の録画を受け取ったら、同じ適格性判定・時間帯・観測ビルド条件・計算法で比較する。ステージ制作の比較では共通の基礎値の版を固定し、基礎値が変わった録画は分ける。開始経路、機体強化、XP設定、ボーナス利用、プレイヤーの感想、性能比較なら実行環境も揃えるか差を明示する。前後のゲーム版と変更項目を確認し、他の同時変更がある場合は単一パラメータの効果と断定しない。

共通に観測した範囲で、前→後のラン単位の分布と差、ラン数・打ち切り、体感の変化、残る不確実性を示す。必要なら効果量や信頼区間を使い、前提と計算法を添える。最小標本数を一律に決めず、少数ランの結果を全体の勝率や最適値へ一般化しない。

仮説を支持した点と競合説明が残る点から、次に必要なステージ/時刻・開始条件・ビルド・共通設定・プレイヤー条件を提案する。変更を少数に絞り、複数条件を同時に動かした結果を単一変更の効果としない。再試遊を提案できるが、自動プレイは依頼がある場合だけ実行する。

## 出力と作業の境界

回答は次の形を目安に簡潔にする。詳細は求められたときに展開する。

```text
結論：この目的には十分 / 条件付き / 不足（理由を1〜2文）
対象：調整モード・目的・対象ステージ・変更候補の範囲
基準：既存目標・仮/確定/未決、今回必要な相談事項
記録：採用ファイル・秒範囲・開始区分・終了状態・比較条件
除外/制約：ファイル別の理由、版/設定/欠測の不明点
観測：目標との差、ラン単位の分布・中央値等・ばらつき、ラン数・観測範囲と根拠
仮説：原因候補と確かめ方（観測と区別）
調整候補：固有/共通の区分、対象項目、現在→候補、狙い、再試遊で見る値と感想
基礎側への相談：ステージ制作の範囲で解決できない課題と必要な判断
前後比較：分布と差・件数・打ち切り・限界（必要なら効果量/信頼区間）
次の試遊：残る仮説を確かめるために揃える条件
優先する記録不足：今回の判断を妨げるものだけ
```

基準設定の相談・分析・候補の提示までを行う。目標の採用と、設定・ゲーム・記録処理の実装は、利用者が決めて依頼した範囲で行う。このスキル自体は数値変更の自動実施権限を与えない。Godot 起動・import、テスト、Git操作・公開はそれぞれ依頼範囲と AGENTS.md に従う。私用ログを編集せず、録画本文・個人情報・利用者固有パスを共有文書へ保存しない。

## Codex / Claude から使う

- Codex：ルートの `.agents/skills/` にあるこのスキルを使い、`$speed-balance-analysis` と入力録画・感想・目的を指定する。検出されない環境では `SKILL.md` のパスを直接渡す。[Codex のローカル配置](https://developers.openai.com/codex/build-skills)
- Claude：このリポジトリの `CLAUDE.md` が参照する `AGENTS.md` と、`.agents/skills/speed-balance-analysis/SKILL.md` を読むよう直接依頼すれば同じ手順を使える。Claude Code の自動検出先は `.claude/skills/<名前>/SKILL.md`。その入口が必要ならスキルフォルダ全体を配置し、本文のリポジトリ相対リンクが元のファイルを指すことを確認する。正本はこのフォルダで管理する。[Claude Code のスキル配置](https://code.claude.com/docs/en/skills)

依頼例：`この SKILL.md に従って、指定した recordings フォルダのステージ4を分析。モードは基礎調整、目的は中盤の成長速度。感想は「180〜240秒に選択が少なく感じる」。通常開始の録画を優先し、調整は提案まで。`
