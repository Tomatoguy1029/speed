# SPEED 設計書

- demo のコードは引き継がない。ゲームの挙動は仕様書を正とし、ここでは Godot での正式な開発に向けて設計し直す。
- 「決定」は決まったもの、「案」はまだ決まっていないもの。
- Godot プロジェクトは `speed/`（`res://`）。`.godot/` などの生成キャッシュはコミットしない。

---

## 1. 前提

設計を縛る条件。仕様書と企画書から来ている。

| 条件 | 出どころ |
|---|---|
| 敵が1300体前後いる場面でも 60fps | 仕様書 21 |
| 商用のゲームとして出す。最初は Steam、最終的に itch.io とスマホのストアにも出す | 企画書 1 |
| 特定の解像度・縦横比に固定しない | 仕様書 17、AGENTS.md |
| 見栄えは非常に重要。独自のシェーダーと描画の流れを作る | ユーザーの方針 |

| なぞり中、機体は0.5実秒で最大数千単位を移動する（1回の更新で大きく動く） | 仕様書 6.5 |

| ステージごとに、星系の広いフィールド・中ボス・フィールドの仕掛けが変わる | 仕様書 2〜22 |

| ストーリーの進み具合・伝説のモジュール・ハイスコアを保存する。伝説のモジュールは能力値に効かない | 仕様書 14・2.3 |

## 2. 技術スタック

| 項目 | 現状 | 案 | 決めること |
|---|---|---|---|
| エンジン | Godot 4.6（`speed/project.godot`） | そのまま | — |
| 言語 | **決定**：GDScript | 大量処理（敵の移動・格子・当たり判定など）は、後から GDExtension（C++）に差し替えられる境目にしておく | GDScript だけで1300体・60fps を出せるかは、実装の段階で小さな試作を作って計測し、C++ が必要か判断する |
| レンダラ | Forward+ | **決定**：PC・スマホは Forward+ か Mobile。ブラウザは Compatibility で、10章の描画の流れの簡易版を動かす | Forward+ と Mobile のどちらにするかは、実装で比べられる段階で決める |
| 物理エンジン | 3D に Jolt を設定済み | 2D の物理エンジンは敵・弾の当たり判定に使わない（7章） | 3D の設定は使わないので外すか |

**言語を決めた理由**：ブラウザ版も出すため。C# は Godot 4.6 でもブラウザへ正式に書き出せない（試作の段階）。GDScript と GDExtension（C++）は、PC・スマホ・ブラウザ・家庭用ゲーム機（W4 Games 経由）のすべてに出せる。Brotato のように、GDScript のサバイバー系が家庭用ゲーム機まで出ている例もある。Godot 公式の説明では、エンジンの機能を呼ぶ処理が多い場合の速さは GDScript と C# で同程度で、差が出る純粋な計算の大量処理だけを C++ に移せばよい。

## 4. 全体の構成

### 4.1 層と依存の向き

**決定**：Godot の商用タイトルの事例（GodotCon 2024、Epictellers）にならい、4つの層に分け、依存は一方向にする。

| 層 | 中身 | 依存してよい相手 |
|---|---|---|
| 道具 | `addons/`。ゲームに依存しない | Godot 本体だけ |
| Manager | ゲームのルールと状態（4.3） | 道具、ほかの Manager（4.4の決まりに従う） |
| UI | HUD、3択、画面 | Manager を読むだけ。状態を書き換えない |
| コンテンツ | ステージ、ボス、フィールドの仕掛けのシーン | Manager、道具 |

Manager は特定のステージ・ボス・仕掛けを知らない。コンテンツの側が Manager に自分を登録して使う。

### 4.2 混合方式

**決定**：大量にあるもの（敵・弾・破片・経験値など）はデータとして持ってまとめて描き、1つずつのもの（中ボス・ラスボス・フィールドの仕掛け・UI）はノードで作る。

| もの | 持ち方 | Manager との関わり |
|---|---|---|
| 敵・弾・破片・経験値 | Manager の配列 | Manager が直接動かす |
| 機体 | ランの状態（データ） | 機体のノードは見た目だけ |
| 中ボス・ラスボス・フィールドの仕掛け | ノード（LimboAI・タイムラインを使う） | 役者として Manager に登録する。決まった順番で呼ばれ、当たり判定の円を登録し、イベントを積む |

### 4.3 Manager

**決定**：スクリプトは Manager で管理する。アプリ全体の Manager だけを Autoload にし、ラン中の Manager はランのシーンの子にする。ステージが終わるとラン中の Manager はシーンごと消える。

**アプリ全体（Autoload）**

| Manager | 担当 |
|---|---|
| GameManager | 画面・モード・ステージ進行の状態機械。シグナルの中心 |
| SaveManager | セーブ、図鑑、伝説のモジュール、ハイスコア、強化画面での強化（11章） |
| ConfigManager | 調整値（`.tres` の実行時の複製。8.3） |
| AudioManager | 音 |
| PlayRecorder | 開発版だけ：プレイの記録（14.3）。F9 で待機を入・切、F10 で記録のフォルダを開く |

**ラン中（ランのシーンの子）**

| Manager | 担当（仕様書の章） |
|---|---|
| RunManager | 時計（実秒・世界秒）、各 Manager の更新の順番、勝敗（4） |
| ShipManager | 機体の移動と HP（5） |
| DrawManager | ゲージ、描画、なぞり、勢い（6） |
| CombatManager | 当たり判定の格子、ダメージ、ヒットストップ（7） |
| EnemyManager | 雑魚の配列、出現、動き（11） |
| BossManager | ボスの役者の登録と形態（12） |
| ProjectileManager | 弾と破片、敵の攻撃の形（仕様書 11.7） |
| BuildManager | 経験値、レベル、3択、武器・特性の発動、リロール（8・9） |
| PickupManager | ドロップと回収（10） |
| HeroManager | 英雄の星座の配置と解放、特別な枠の力の発動とクールダウン、目印の星の選定と位置のヒント（8.1・13.1） |
| FieldManager | 地形、隕石、フィールドの仕掛け（13） |
| FinaleManager | ラスボス戦の締め（12.4） |
| RenderManager | 描画の流れ（設計書10章） |

**更新の順番**：各 Manager は自分で `_physics_process` を回さず、RunManager が1回の固定更新ごとに次の順で呼ぶ。順番は demo の更新の順番に合わせる（`scripts/managers/run_manager.gd` の `_play_tick`）。

1. 入力を読む（9章）、描画の操作（DrawManager）
2. ヒットストップ（止まっている間は以降を飛ばす）
3. 戦闘の準備（CombatManager）、ゲージ・描画・なぞり（DrawManager）
4. 世界の速さを決める（実秒と世界秒、5章）
5. フィールド、敵、ボスの動き
6. 当たり判定の格子を作り直す
7. 機体の移動と接触
8. 英雄の星座と目印の星の更新、力の発動（HeroManager）
9. 武器・特性の発動（BuildManager）
10. 弾・破片の動きと命中（ProjectileManager）
11. 倒した敵の片付け、敵の出現
12. ドロップと回収（PickupManager）
13. カメラ
14. 勝敗、保留していた3択

**やり取り**

- シグナルは、回数の少ないもの（ステージ開始、レベルアップ、ボス出現、クリアなど）に使う。
- 命中・撃破のように回数の多いものは、1回の更新ごとのイベントのリストに積み、表示・音・UI が読む。
- UI と入力から Manager への働きかけは、RunManager への命令（カードを選んだ、線を確定した、など）として渡す。

### 4.4 守る決まり

**決定**

1. 1つの Manager の責任は、仕様書の1つの章に対応させる。何でも入る Manager を作らない。
2. Manager 同士は勝手に参照し合わない。必要な相手は RunManager が初期化のときに渡し、依存の向きは `RunManager._wire()` で一覧できるようにする。
3. 状態と処理を分ける。ランの状態は RunState にまとめ、Manager は処理を持つ。
4. 依存は4.1の一方向に限る。Manager はコンテンツに依存しない。
5. 決まりは、自動で確かめるチェックとして書く（Manager がコンテンツを参照していないか、など）。
6. 実験は `gyms/` で行い、うまくいったものを決まりに沿って作り直してから取り込む。

## 5. 時間

**仕様から来る条件**：実秒と世界秒の2つの時間がある。描画中は世界が0.1倍、なぞり中は「260 ÷ 突進の速さ」倍、ヒットストップでは止まる。ランの時計・ゲージ・なぞりの0.5秒は実秒。ポーズと3択ではすべて止まる。

**案**

- `_physics_process` の固定更新で全システムを進める（回数は下の決定）。
- `RunClock` が毎回 `real_dt` と `world_dt`（＝ `real_dt` × 世界の速さ）を計算し、各システムに渡す。各数値をどちらの時間で数えるかは仕様書に従う。
- `Engine.time_scale` は使わない。UI や実秒で動くものまで一緒に遅くなり、2つの時間を分けられないため。
- ポーズは RunManager が更新を止めて実現する。`get_tree().paused` は UI の扱いが複雑になるので使わない。
- 表示は 2D の物理補間で滑らかにする。60Hz を超えるモニターでも、なめらかに見えるようにするため。

- ラスボス戦の締め（仕様書 12.4）の「止まった世界で描く」段階は、世界の速さを0にして実現する。描画と UI は実秒で動くので、この仕組みのまま扱える。自動の演出（叩き込む段階）は実秒で進める。

**決定**：固定更新は1秒に120回。入力・線・機体・武器は毎回進め、敵・ボス・天体・格子・弾・出現・回収（世界側）は `config.world_tick_div` 回に1回（2で60Hz）、たまった `real_dt`・`world_dt` でまとめて進める。各処理は1回あたりの時間（dt）を使って書き、回数を前提にしない。すり抜けは更新の回数ではなく、線分と円の判定（7章）で防ぐ。

## 6. 大量の敵・弾・ドロップ

4.2の決定に従い、敵・弾・ドロップはデータとして持つ。

**仕様から来る条件**：敵1300体前後、経験値の結晶は最大600個、機雷は最大250個、ほかに弾と破片がある。スマホでも 60fps。

**実装**

- 敵・弾・破片・経験値の結晶・部品は、項目ごとの数値の列（`PackedVector2Array`・`PackedFloat64Array` など）で持つ。1行が1つの物で、i 番目の物は各列の i 番目。ほかの処理から読むときは、ループの前に列を手元の変数へ取り出す。
- 生きている物は、消えるまで同じ行にいる。消えた行は空きになり、次に加える物が使い回す（`scripts/common/row_slots.gd`）。毎回の更新では、その回に変わる列だけを書く。使用中かどうかは `alive` の列で表し、ループは使用中の行だけを処理する。空きが尽きたら全部の列をまとめて伸ばす。
- 行を加える・空きに戻す・列を伸ばすのは、その列を持つ Manager の関数。1組の列は、名前の頭（`hostile_`・`friend_`・`gem_`・`coin_`）か、列だけを持つクラス（`EnemyTable`）でまとめる。デバッグ版では次を確かめ、確かめる列は名前の頭やクラスから自動で集める（`scripts/common/columns.gd`）。
  - 列を伸ばしたとき、全部の列の長さがそろっているか。
  - ラン開始時、追加の関数が使い回す行の全部の列を書き直すか。書き忘れた列があれば、その名前を出して止まる。
- 敵は敵の表（6.2）の1行。隕石とボスの当たり判定も同じ表に入る。撃破した敵は撃破済みの印を付け、その回の終わりに行を空きへ戻す。何フレームもまたいで敵を覚えるときは、行番号と id の組で覚え、`EnemyManager.is_same` で確かめる。行動する雑魚は行動の種類ごとの行番号の一覧に入り、更新は種類ごとにその一覧を回す。追跡の更新は関数を呼ばずにループの中で計算する。画面から遠い敵は、判断（向きを変える・攻撃の時間を進めるなど）を3回に1回だけ、まとめた時間で行い、間の回は今の速度で進むだけにする。さらに速さが要るときは、ここを GDExtension に移す。
- 経験値の結晶の上限で「いちばん古い結晶」を選ぶため、結晶ごとに落ちた順の通し番号を持ち、落ちた順の待ち行列から取り出す。拾われた結晶は取り出すときに読み飛ばす。
- 当たり判定の格子（`SpatialGrid`）は `PackedInt32Array` の先頭・次の表で持ち、探索の結果は敵の表の行番号。
- 出現調査は世界側の更新ごと。全体数・四辺の偏り・遠方の再配置は毎回調べ、種類別数は出現上限を使う戦艦とタイタンだけ集計する。四辺の分類では個体ごとの正規化除算を交差乗算に置き換える。
- 描画は `MultiMesh` にまとめて描く（`scripts/render/instance_batch.gd`）。Compatibility では `custom_aabb` の設定が要る。
- 機体とボスは1体ずつなので、ノードにする。ボスは部位（首など）を子として持ち、部位ごとに当たり判定・HP・攻撃を持てるようにする。当たり判定は7章の自前の判定に部位の円を登録する。

### 6.1 敵とボスの AI

**決定**

| 対象 | 層 | 方式 |
|---|---|---|
| 雑魚 | 行動 | 種類ごとの単純なステートマシン（例：ダーターの予告 → 突進 → 回復） |
| 中ボス・ラスボス | 形態（第1形態 → 第2形態 → 最後の抵抗 など） | 階層型ステートマシン |
| 中ボス・ラスボス | 判断（各形態の中で、状況を見て次の行動を選ぶ） | Behavior Tree |
| 中ボス・ラスボス | 攻撃（1つ1つの動き・弾・予告の振り付け） | タイムライン（エディタで人が調整する） |

- 道具は LimboAI（MIT ライセンス。Behavior Tree と階層型ステートマシン、編集画面とデバッガを持つ）の GDExtension 版を使う。Windows・macOS・Linux・Android・iOS・Web に対応している。GDExtension 版で使えない機能は導入前に確認する。
- ボスの判断の層から、自機の状態（線を描いているか、描かれた線、ゲージの溜まり具合、位置）・フィールドの仕掛けとの位置関係・ボス自身と部位の HP を読めるようにする。何を判断に使うかは、ボスごとの仕様で決める。

**うみへび座の役者**

`scenes/bosses/hydra_boss.tscn` と `scripts/bosses/hydra_boss.gd` が本体・首・頭を組み合わせる。本体と頭の当たり判定は敵の表に登録し、首の節は役者が描く。頭の位置・向きは攻撃の処理が決める。頭の行は親の本体の行と結び、行の再利用を ID でも確かめる。`EnemyManager.cleanup()` は行を解放する前に `BossManager.part_defeated()` から役者の `on_part_defeated()` へ通知し、頭へのダメージと火による再生停止を確定する。

`scripts/bosses/hydra_neck.gd` は通常の首と不死の首の骨組みを CPU で計算する。付け根から頭までの点列を持ち、世界秒で進む波を曲がりの目標へ加え、FABRIK の往復で節長を補正する。描画時は両端を本体と頭へ固定し、補正の残差を先端の節で吸収する。引いた首は余長を曲がりに使い、頭が全長より遠くへ出ると首全体を伸ばす。伸びきった首は直線で確定し、縮みきった首は更新と描画を止める。節数・補正回数・余長・波・追従の調整値は `data/bosses/hydra.tres` の `params.neck_*` に置き、骨組みの点列を描画素材から分けて扱う。 描画命令は世界の更新・部位の消失・本体の移動・半径の変更で更新し、停止中はキャッシュを使う。描画用の半径キャッシュは役者のメタデータに持ち、実験場の戦闘状態の比較から分ける。

強めの技は `AnimationPlayer` のタイムラインを世界秒で進める。Behavior Tree が必要な首のそろった技を選び、役者が羅針盤の予告と各首の動きをまとめて扱う。必要な首が落ちたときはタイムラインを止める。首ごとの通常攻撃・生え直しは役者の状態で持ち、仕様は [仕様書](spec.md) の12.3。

## 7. 当たり判定と空間分割

**仕様から来る条件**：円同士の判定が中心。なぞり中は1回の更新で長い距離を進むので、点の判定では敵をすり抜ける。線の左右45の帯との判定がある。地形（惑星・月）で弾・線・敵が止まる。

**案**

- Godot の物理エンジン（`Area2D`・`RigidBody2D`）は使わず、自前で判定する。数が多く、判定のルールも独自のため。
- 一様な格子で空間を分け、毎回の更新で敵の位置から作り直す。配列は使い回す。格子の範囲は保持し、敵が範囲外へ出たときだけ全件から求め直す。前回使ったセルだけ初期化する。
- なぞりは「線分と円」の判定で、通った区間を漏れなく調べる。
- 地形の詳細判定は線分と円で調べる。天体の範囲を512単位の格子へ毎更新登録し、短い移動区間では線分の太さを含む矩形に重なるセルから候補を取る。長い区間や格子外では全天体を調べる。敵の近傍確認では、月を軌道の半径帯に登録して候補を絞る。雑魚は、前回確かめたときの天体の表面までの距離・位置・世界時刻を持ち、その距離からその後に動いた距離と月が動けた距離を引いても余裕が残る間は、近傍確認を省く。敵の弾は等速なので、いちばん近い天体の表面までの距離を弾ごとに持ち、弾の移動量と月の公転の速さの上限で毎回減らす。この余裕が残る間は天体の判定を省く。月の軌道半径・大きさがラン中固定であることを利用し、周回位置は毎更新の実位置で判定する。惑星の判定と近傍の条件は維持する。
- フィールドの仕掛けの作りは、それぞれの仕掛けを実装するときに考える。

**決めること**：フィールドが広くなったとき（仕様書 2.2）、遠くの地形・隕石・仕掛けをどう扱うか。demo の隕石と同じく、画面の近くだけ有効にする方式を全体に広げるか。

- 敵の組み合わせ（フォーメーション。`data/formations/*.tscn`）は、置ける種類（`types`）を持つ根の `EnemyFormation` の下に、配置の `FormationLayout`（子に敵1体ずつの `FormationMarker`）と出現位置の `FormationEntry` を何種類かずつ置くシーン。エディターでは、機体・止まっているときの画面の枠・回しても画面に入らない目安の円を描き、選んだ配置を出現位置に重ねて見せ、円の内側に入る敵や、置ける種類にない敵があれば警告する。置き場所の敵の種類は、置ける種類の中から選ぶ。出現位置の向きは自動で機体の方を向く。ゲーム中は、組み合わせごとに一度だけシーンを読んで位置と向きの一覧にする（`EnemyManager.formation_data`）。

### 8.4 データ編集ツール

**決定**：`.tres` を Godot のインスペクタだけで編集するのは扱いにくいので、Godot エディタの拡張として専用の画面を作り、データをまとめて管理できるようにする。

- 情報が見やすく、調整しやすい形にする。
- 見やすくするために情報を隠さない。すべての値をその画面で見られるようにする。

## 9. 入力

**仕様から来る条件**：PC はマウス、スマホはタッチ、キーボードは補助。ゲームパッドは一旦対応しない。

機器ごとの入力を、`scripts/input/intent.gd` の意図にまとめる。

| 意図 | マウス | タッチ |
|---|---|---|
| 移動：進みたい向きと強さ | カーソルの向き（強さは一定） | 仮想スティックの向きと倒し具合 |
| ペン先：描く位置と押した瞬間 | カーソルの位置とクリック | 指の位置と「描く」ボタン |

- 移動とペン先のほかに、描画の補助（`alt_press`）と英雄の星座の力の発動（`hero_press`）を、押した瞬間の意図として渡す。`RunManager` が `hero_press` を受けて `HeroManager.activate()` を呼ぶ。
- ゲームのシステムは変換された意図を読む。機器を足すときは、変換するところだけを足す。
- キー操作は Godot の InputMap で定義する。設定画面で変えたキーの割り当ては、設定のファイルに保存し、起動時に InputMap へ反映する。

## 10. 描画と演出

**決定**：2D のまま、層に分けて描き、シェーダーの段を重ねる自前の描画の流れを作る。

- 背景・敵・演出などを別々の描画先（SubViewport）に描き、それぞれにシェーダーを重ね、最後に合成する。
- 各段は、PC・スマホ用（HDR・コンピュートシェーダーを使える）とブラウザ用の簡易版に差し替えられるようにする。
- 背景の星は、開始時に共通の円メッシュと400個の乱数配置・色をMultiMeshへ登録して使い回す。位置・視差・ズームは頂点シェーダーで計算し、毎フレームは視点のパラメータだけ更新する。既存の乱数シード・星の大きさ・色・視差の式を維持する。
- 法線マップを持つ敵は、カメラに追従する `EnemyLighting` CanvasLayerでベース・装甲のMultiMeshと予告を重ねる。DirectionalLight2Dの照射先をこのCanvasLayerに限定する。装甲シェーダーは個体の変換行列で法線を回し、被弾フラッシュと敗北時の減光を描画へ適用する。照明設定は `data/visuals/enemy_lighting.tres` に持ち、実験場から同じリソースを編集・保存する。実験場がHDRの本番映像を通常のUIへ合成するときは、表示色をsRGBへ変換する。
- 敵弾の赤い円と暗い中心は開始時に共通のメッシュを作り、MultiMeshでまとめて描く。位置と半径だけを各インスタンスへ渡す。画面外の描画除外・弾の更新・寿命・攻撃頻度は維持する。
- ゲームの処理と描画は完全に分ける。ゲームの処理は「何がどこにあるか」だけを持ち、描画側が層ごとに描き分ける。
- **決定**：スクリプトで描いている図形（`_draw` の円・矩形・弧など）は、すべてスプライトに置き換える。大量に出る物はすべて MultiMesh でまとめて描く。
- Godot の Compositor は3D専用なので使わない。
- **決定**：シェーダーは実装できるところからどんどん作る。コンピュートシェーダーは演出（破片、光の跡、背景、光のにじみ、波動の歪みなど）に積極的に使う（PC・スマホ。ブラウザの Compatibility では使えないので簡易版で代える）。ゲームの処理（敵の移動・当たり判定など）には使わない。ただし計測で GDScript では回らないと分かった場合は、C++ とあわせて比較の候補に入れる。
- 案：見た目はすべて1つの 2D の世界に置き、背景・敵・演出などを層の番号（`visibility_layer`）で分ける。層ごとの SubViewport が同じ世界を共有し、自分の番号のものだけを描く（`canvas_cull_mask`）。

- 描いている線・なぞった跡は、線の点の列から描く。
- 破片・火花・炎などの大量の演出は、6章と同じく配列とまとめた描画で扱う。スマホの性能を考えて、GPU のパーティクルに頼り切らない。
- 画面外の演出は描画だけ省き、位置・寿命の更新は続ける（カメラが動けば同じ状態が見える）。
- 画面の拡大縮小は、表示を伸ばす方式（`canvas_items`）と、縦横比に合わせて広げる設定（`expand`）を使う。カメラのズームは画面の短い辺を基準に計算する（仕様書 15）。

## 11. 保存

- `user://` に保存する。中身は仕様書 14 のとおり（ストーリーの進み具合、伝説のモジュール、ハイスコア、図鑑の獲得状況を含む）。
- データに版の番号を持たせ、版が変わったら古いデータを新しい形に変換する。読めないデータは壊さずに初期値で始める。
- 設定（音量、画面モード、言語、キー設定）は、セーブとは別のファイルに保存する。

## 12. UI

- すべての UI は `Control` で作り、アンカーとコンテナで画面の大きさに合わせる。座標を決め打ちしない。
- 色と文字の大きさは1つのテーマにまとめる。強化段階の色（仕様書 8）もテーマで管理する。
- 3択・ポーズ・結果は、ラン中の状態を表示するだけにする。選んだ結果は RunManager に命令として渡す（4.2）。

## 13. 音

- 音の再生口を使い回し、同時に鳴る数に上限を設ける。
- バスを「全体」「効果音」「エンジン音」に分ける。
- 方向性は未決（仕様書 18）。

### 14.1 ステージ・実験場を直接起動するエディタ拡張

**決定**：特定のステージをエディタから直接プレイできるエディタ拡張を作る。仕組みは別プロジェクト（gamejam-2/record の `addons/debug_launcher`）と同じにする。

- エディタのツールバー（「2D／3D／スクリプト」の並びの直後）に「▶ ステージ」「▶ 実験場」の順でボタンを置く。
- 「▶ 実験場」は `EditorInterface.play_custom_scene()` で `gyms/enemy_lab/enemy_lab.tscn` を直接起動する。編集対象のシーンはそのまま保つ。
- 押すと起動先のステージを決める：編集中のものがステージならそれ → 直前に起動したステージ → ステージ1。編集中のシーンは保存してから起動する。
- 起動先を `user://` の設定ファイルに「1回だけ有効な予約」として書き、メインシーンを実行する。project.godot は書き換えない。
- ゲーム側は起動時、エディタから実行したときだけ予約を読み、すぐ消してからそのステージへ直行する。予約がなければ通常どおりタイトルから始める。F5 の挙動は変えず、製品版ではこの経路に入らない。
- 予約は開始時刻も持てる（出現タイムラインの「再生」）。開始時刻があれば、ランの時計をその時刻から始める。

### 14.2 出現タイムラインのエディタ拡張

**決定**：ステージの時間帯と出現のクリップを、動画編集のようなトラックで並べて編集するエディタ拡張（`addons/spawn_timeline/`）を作る。

- インスペクタでステージ（時間帯の `phases` と出現のクリップの `clips` を持つリソース）を開くと、エディタの下のパネル「出現タイムライン」に表示する。中身はプロパティ名で読み書きし、Godot 本体だけに依存する（4.1）。
- 上から、時刻の目盛り、時間帯（区間と名前）、雑魚の補充の目標の数のグラフ（曲線があればその合計）、雑魚の目標の数の曲線（種類ごとに1行）、クリップのトラック（1本に複数のクリップを置ける。一番下は新しいトラック用の空の行）を並べる。クリップは、開始から長さの間の棒に、名前・種類・同時の群れの数・出す間隔を書いて描く。クリップのトラック（`track`）が -1 なら、クリップの並びの番号のトラックに置く。フォーメーションに、クリップの種類の組み合わせにない敵を置いているクリップは赤く囲む。
- ドラッグで変えるもの：時間帯の境目（開始の時刻）、クリップの開始とトラック（棒を左右・上下に。落とした先でほかのクリップと重なるなら元に戻す）と長さ（右端）、雑魚の曲線の点。曲線の何もない所をダブルクリックで点を足し、点をダブルクリックで時刻と数を入力し、↑↓で選んだ点の数を1ずつ（Shift で10ずつ）変え、Delete で選んだ点を消す。「通常」で空の通常トラックを追加し、通常トラックの空き部分をダブルクリックしてクリップを置く。空の通常トラックも `track_names` の要素として保持する。「雑魚敵」でステージの敵のうち雑魚（敵の定義の `rank` が 1）から種類を選び、時間帯・合計表示の下にまとまった雑魚敵トラックの末尾へ曲線を追加する。Shift を押しながらのドラッグは 0.1 秒刻み。クリップ（棒）・トラック（左の欄。ステージの `track_names` に入る）・時間帯の名前は、ダブルクリックで変える。クリップは右クリックのメニューと ⌘C・⌘V・⌘D で、コピー・貼り付け（再生位置の時刻に）・複製（すぐ後ろに）ができ、重なるときは空いているトラックへ置く。トラックは、左の欄の名前をクリックすると選ばれ、Delete でクリップごと削除（下のトラックが詰まる）、⌘D でクリップごと複製（すぐ下に）できる。名前をつかんで上下に動かすとトラックが浮き、落とした所（トラックの間）へクリップと名前ごと差し込む。右クリックのメニューでも複製・削除ができる。名前のないトラックは「トラック 番号」と表示し、その形の名前は保存しない。クリップは追加・削除できる。ホイール・2本指の縦スクロールで上下に、Shift＋ホイール・2本指の横スクロールで左右に動かし、Ctrl（⌘）＋ホイール・ピンチ・上部のボタンで拡大縮小する。上段は「雑魚敵」「通常」「ボス」「終了」「-」「+」「最大」「再生」、再生位置、ルール違反のクリップ数の順に並べ、丸い「？」だけ右端に固定する。「最大」と初期表示は0:00〜11:00が収まるスケールにする。終了ピンがなければ、エンドレス用に180分まで横へ移動できる。文字と行の大きさはエディタの表示倍率に合わせる。クリップのトラックは縦にスクロールし、目盛り・時間帯・雑魚の数の行は上に留める。タイムラインはエディタの上部の画面のタブ「出現タイムライン」にも表示する。
- 時間帯と同じトラックに、ボス出現・ステージの制限時間をピン、敵の強化区間を帯として重ねる（`stage_clocks.gd`）。上段の「ボス」「終了」は、共通のピンのアイコンを付け、同じ幅で横に並べる。ONは灰色のボタン、OFFは背景・文字・アイコン全体を暗く表示する。押すと再生位置へ配置し、もう一度押すと削除する。再生位置が先頭なら既存の配置の末尾へ置く。ボスピンの配置・削除はステージの `boss_enabled` を切り替える。ピンは左右のドラッグで時刻を変え、画面の端でつかみ続けると横へスクロールする。強化帯は左右の端で開始・終了、中央で区間全体を動かす。ダブルクリックで時刻を入力し、時間帯の右クリックから制限時間の追加・解除、強化の継続、共通設定への復帰を選ぶ。共通設定のリソースはプロジェクト設定 `spawn_timeline/defaults_resource` から読み、ステージの上書きがあれば優先する。表示範囲はこれらの進行時刻も含める。
- 編集はエディタの取り消し・やり直しに載せ、確定するたびにステージと、別ファイルの時間帯を保存する。
- インスペクタでは、ステージの敵の一覧（`enemies`）と、クリップの種類の組み合わせ・フォーメーションの置ける種類（`types`）を、チェックボックスで選ぶ。クリップの使う並び（`layouts`）も、クリップのフォーメーションの配置（置き場所を持つ子のノード）をチェックボックスで選ぶ。チェックボックスの並びは見出しで折りたためる（ステージの敵の一覧は初めは折りたたむ）。クリップの種類は、タイムラインで開いているステージの敵の中から選ぶ。敵の定義の場所はプロジェクト設定 `spawn_timeline/enemy_dir` から読む。
- 目盛りをクリックして再生位置を決め、「再生」でその時刻からステージを起動する（14.1）。

### 14.3 プレイの記録

**決定**：ステージの調整に使うため、遊んだランのデータをファイルに書き出す。集計はせず、記録を読む側（AI など）が行う。

- 開発版だけで動く Autoload（`scripts/managers/play_recorder.gd`）。F9 で記録の待機を入・切し、待機中に F10 で記録のフォルダを開く。待機中は画面の右下に小さく「● REC 待機」、記録中は「● REC」とランの時計を出し、記録を閉じたら保存したファイル名を数秒出す。
- 待機中に始めたランを、終わる（クリア・やられた・やめた）まで1つのファイルに書く。待機は F9 で切るまで続き、次のランは別のファイルになる。実験場のランは記録しない。
- 置き場所は書類フォルダの `SPEED/recordings/stage<番号>_<日時>.jsonl`（Mac は `~/Documents/SPEED/recordings/`。書類フォルダが分からなければ `user://recordings/`）。ほかの開発者もこのファイルを送って共有する。1行に1つの記録（JSON）。書いたそばからファイルへ出し、メモリにためない。
- 記録の種類（`type`）：
  - `start`：ステージ、始めた時刻、日時、まとめる間隔、時間帯の一覧（名前・開始）
  - `sample`：3秒（ランの時計）ごとのまとめ。拾った・落ちた・フィールドに残る経験値、レベル、HP、敵の数（星ごと・画面の中）、種類ごとの撃破数、倒した原因ごとの撃破数（`kills_by`）、与えたダメージの原因ごとの合計（`dealt`。倒しきった余りも含む）、攻撃の種類ごとの被弾（撃った敵が分かる攻撃は「攻撃/敵の種類」）、攻撃の予算の使用量の最大
  - `band`：時間帯の切り替わり（名前）
  - `levelup`・`pick`：レベルアップと、出たカード・選んだカード・おまけで上がった数
  - `strong`：強敵と大物（星3以上）が倒れた（ランの終わりにまだいた）ときの、出た時刻・生きていた時間・受けた体当たりの回数・武器のダメージの合計と原因ごとの内訳（`by_cause`）・とどめの原因（`killed_by`）
  - `clip_group`・`clip_group_end`：出現のクリップの群れが出た・全滅した
  - `end`：終わり方、レベル、撃破数、武器と特性、やられたときは最後に受けた攻撃
- ゲーム側は、記録のために出来事（`strong_spawn`・`clip_group`・`clip_group_end`、撃破と命中の個体の `id`、被弾の `source`）と、経験値の合計（`RunState.xp_gained`・`xp_dropped`）を出す。

## 19. 敵・ルート実験場

`gyms/enemy_lab/` がデバッグ専用画面と編集・記録・隔離試行を担当する。`LabSession` は `scenes/run/run.tscn` を初期化し、共有データから複製した設定、seed、定義、入力元を `RunManager.options` へ渡す。通常ランは既定の参照と保存先を使う。実験ランは外部から固定 tick を進め、結果保存の代わりに実験イベントを受け取る。閲覧用キャンバスは本番の敵表と攻撃表を読み、変更を命令としてセッションへ渡す。

再現の基準は初期条件と tick 付き命令履歴の再実行。ConfigManager は読み込んだ定義のハッシュを持ち、セッションがその基準を保持する。明示的なデータ再読込は敵・ボス・時間帯・ステージ・共通値を新しい参照として公開し、既存の実験が持つ参照を保つ。実験用の描画時計は `RunState.sim_time`、ボスの戦闘乱数は `RunState.rng` を使う。手動更新するボスのタイムラインはメソッドをその更新内で実行する。巻き戻しの高速化は、停止したランシーンを上限付きで保持する方式で、HSM・BT の内部状態も同じ実体で復元する。チェックポイントの鍵は適用済みの初期条件・命令列。履歴を差し替えた場合は実行済みの鍵との一致を検査する。

`route_trial.gd` は独立したセッションで DrawManager の描画・なぞりと各 Manager の本番判定を実行する。`scripts/encounters/route_constraints.gd` は戦闘の別実装を持たず、静止形状と保守的な時間包絡の検査を担当する。成立区分と操作の正は [仕様書20.1](spec.md#201-敵ルート実験場)。

`scripts/encounters/attack_director.gd` は要求・分類の同時取得・待機・開始・残留・終了を管理する。ProjectileManager の行番号から攻撃グループを引き、行の再利用時に対応を上書きする。付着範囲の所有者と、発生元・攻撃グループを区別する。EnemyManager の発動境界とボスの判断から予告前に許可を取り、攻撃のない追跡は既存の処理で進める。実験の複数ボスは、個体ごとの BossManager が本体と役者を所有し、部位通知と撃破を対応する行・IDへ送る。

`encounter_coordinator.gd` はルートと配置領域から候補を構成する共通境界を持つ。採用された `StageDef.encounter_profile` が有効なランで攻撃管理と出現へ接続し、時間帯と基準ハッシュを検査する。本番での候補採用は標準サイズ・レベル1の通常敵を対象とし、特殊な条件は実験の隔離再生で確認する。通常設定が空なら追加の検査器と攻撃管理を生成しない。
