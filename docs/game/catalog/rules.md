## 本番の数値パラメータ

本番では、数値のパラメータの正は Godot の `.tres`（[設計書](../architecture.md) 8章）とし、ドキュメントでは管理しない。本番の一覧には、ID・名称・採用状態・効果の内容・ルートへの影響・実装状況と `.tres` の参照先を書き、数値は書かない。下の更新ルールのうち数値に関する部分は、本番では `.tres` に対して行う。

demo から引き継いだ初期値は `speed/data/` の `.tres` へ移し、本番の一覧と仕様書から外した（2026-10-08）。仕様書は数値の代わりに `config.xxx`（`speed/data/config.tres` の項目）やデータのファイルを示す。demo の一覧は今のまま数値を記録する。

## 状態の読み方

採用判断と実装状況は別に記録する。既存処理があっても新方式への採用が決まったことにはならない。

| 採用状態 | 意味 |
|---|---|
| 候補 | 検討対象。個別の仕様・採用は未確定 |
| 採用 | ユーザーが採用を決めたもの。未実装のこともある |
| 保留 | 通常候補と分けて保持し、採用判断まで抽選に入れない |
| 不採用 | 新方式には含めない。理由と既存処理への参照を残す |

実装状況は対象側の「未実装」「類似処理あり（差を明記）」「実装済み」「旧版の履歴のみ」で区別する。demoだけに実装がある場合、本番の実装状況は「未実装」とし、demoの参照先を併記する。

## 更新ルール

1. 新しい案が出たら、該当一覧へ1行追加する。武器は `W`、特性は `T` に続く連番を付け、削除・改名してもIDを再利用しない。本番・demoの両一覧で既存IDを確認し、別の項目に同じIDを付けない。同じ項目を移植するときはIDを引き継ぐ。敵はコードのtype IDを使い、未実装の案には仮IDであることを明記する。
2. 名前・効果・発動条件・数値・採否・実装状況を変えたら、同じ作業で該当行を更新する。未決事項は未決のまま書き、提案を採用済みにしない。
3. 実装したらコードID／参照先と実際の挙動を記載する。武器のレベル別効果・特性の重ね掛け効果を、対象側で決まった強化上限に合わせて一覧の下にID付き詳細として追記する。未決の数値は埋めない。
4. 経路に関係する効果には「どう通りたくなるか／突破後に何が変わるか」を記録する。単なる数値強化はその旨を書く。
5. 廃止・保留した項目は行を消さず専用の区分へ移し、理由と参照先を残す。削除するコードの保存先が必要ならコミットを示す。
6. 操作・成長・全体バランス・課題・経緯は上の表にある対象側の文書と作業ユーザーの履歴へ記録する。個別の全一覧を別文書へ複製しない。
7. 各一覧の最終更新日を更新する。コードの数値を転記する際は、基礎値・倍率・レベル補正を区別する。変更がない一覧は更新不要。

## 追加時の記入例

- 武器：ID／名称／採用状態／発動・効果／ルートへの影響／実装状況・コードID／未決事項
- 特性：ID／名称／採用状態／発動・効果／ルートへの影響／実装状況・コードID／重ね掛け・未決事項
- 敵：type ID／名称／実装状態／基礎数値／行動・攻撃／出現／未決事項
