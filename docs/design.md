# SPEED 設計書

最終更新：2026-10-08

[仕様書](spec.md) を Godot でどう作るかを書く文書。フォルダ構成、全体の構成、データ構造を扱う。

- demo のコードは引き継がない。ゲームの挙動は仕様書を正とし、ここでは Godot での正式な開発に向けて設計し直す。
- **この文書の内容はすべて案で、まだ決まったものはない。** 各章は「仕様から来る条件」「案」「決めること」に分けて書く。決まったら「案」を「決定」に書き換え、判断の経緯は作業ユーザーの履歴に残す。
- Godot プロジェクトは `speed/`（`res://`）。`.godot/` などの生成キャッシュはコミットしない。

---

## 1. 前提

設計を縛る条件。仕様書と企画書から来ている。

| 条件 | 出どころ |
|---|---|
| 敵が1300体前後いる場面でも 60fps | 仕様書 19 |
| PC を最優先し、最終的にはスマホにも対応する | 企画書 2 |
| 特定の解像度・縦横比に固定しない | 仕様書 15、AGENTS.md |
| 世界の時間と実時間を分けて扱う。描画中0.1倍、なぞり中は可変、ヒットストップで停止 | 仕様書 1・4 |
| なぞり中、機体は0.5実秒で最大数千単位を移動する（1回の更新で大きく動く） | 仕様書 4.5 |
| ほとんどの数値をプレイ中に調整パネルから変えられる | 仕様書 18 |
| 武器・特性・敵は一覧の管理 ID（W01、T01、`drifter` など）で管理する | [catalog.md](catalog.md) |
| ストーリー（5ステージ）とエンドレスの2つのモードがある | 仕様書 20 |
| ステージごとに、星系の広いフィールド・中ボス・フィールドの仕掛けが変わる | 仕様書 20〜22 |
| 中ボスは複数の部位（うみへび座の首など）を持ちうる。画面より大きくなりうる | 仕様書 21 |
| フィールドの仕掛けが、自機の移動と描いた線の両方に作用する | 仕様書 22 |
| ラスボス戦の締めで、描画のルール（長さの上限・世界の速さ）を一時的に変え、自動の演出を流す | 仕様書 23 |
| ストーリーの進み具合・伝説のモジュール・ハイスコアを保存する。伝説のモジュールは能力値に効かない | 仕様書 12・20.3 |

## 4. 全体の構成

### 4.1 シーンの木

```
Main (Node)
├─ Title (Control)            モードの選択（ストーリー／エンドレス）
├─ Station (Control)          出発前の画面
└─ Run (Node)                 ラン中だけ存在する。どのステージ・モードかを受け取って始まる
   ├─ World (Node2D)
   │  ├─ FieldView            惑星・月・宇宙塵・隕石・フィールドの仕掛けの描画
   │  ├─ EnemyView            敵をまとめて描く（6章）
   │  ├─ Boss (Node2D)        ボスと部位（6章）
   │  ├─ PickupView
   │  ├─ ProjectileView
   │  ├─ Ship (Node2D)
   │  ├─ PathView             描いている線・なぞった跡
   │  └─ FxView
   ├─ Camera2D
   └─ Hud (CanvasLayer)
      ├─ GaugeRing / SpeedPanel / Timer / XpBar / Loadout / BossBar
      ├─ CardSelect           3択
      ├─ Pause
      └─ DebugPanel           調整パネル（開発版のみ）
```

### 4.2 ゲームの処理と表示を分ける

- ゲームの状態と処理（敵・弾・ドロップ・ゲージなど）は、ノードではなくデータとして持つ。各「システム」がそのデータを更新する。
- ノードは表示と入力の受け口だけを担当する。表示は毎フレーム、データを読んで描く。
- システムは `RunController` が決まった順番で呼ぶ。1回の固定更新の順番（案）：

1. 入力を読む（10章）
2. 時間を進める（5章）
3. ゲージ・描画・なぞり（`draw/`）
4. 機体の移動（フィールドの仕掛けの力を含む）
5. 敵とボスの出現と動き
6. 当たり判定と戦闘（接触、波動、弾、破片）
7. 武器・特性の発動
8. ドロップと回収、経験値とレベル
9. 勝敗と状態の切り替え（ステージの進行、締めの段階）

- 依存の向きは「データ → システム → 表示」。表示側からシステムを呼ばない。UI からの操作（カードを選ぶ、など）は `RunController` に命令として渡す。

### 4.3 常駐させるもの（Autoload）

最小限にする。

| 名前 | 役割 |
|---|---|
| `Config` | 調整できる数値（8.3） |
| `Save` | セーブの読み書き（11章） |

ランの状態は `Run` シーンが持ち、Autoload には置かない。ランを抜ければ消え、次のランは必ず新しい状態から始まる。

## 5. 時間

**仕様から来る条件**：実秒と世界秒の2つの時間がある。描画中は世界が0.1倍、なぞり中は「260 ÷ 突進の速さ」倍、ヒットストップでは止まる。ランの時計・ゲージ・なぞりの0.5秒は実秒。ポーズと3択ではすべて止まる。

**案**

- `_physics_process` の固定更新（60回/秒）で全システムを進める。
- `RunClock` が毎回 `real_dt` と `world_dt`（＝ `real_dt` × 世界の速さ）を計算し、各システムに渡す。各数値をどちらの時間で数えるかは仕様書に従う。
- `Engine.time_scale` は使わない。UI や実秒で動くものまで一緒に遅くなり、2つの時間を分けられないため。
- ポーズは `RunController` が更新を止めて実現する。`get_tree().paused` は UI の扱いが複雑になるので使わない。
- 表示は 2D の物理補間で滑らかにする。60Hz を超えるモニターでも、なめらかに見えるようにするため。

- ラスボス戦の締め（仕様書 23）の「止まった世界で描く」段階は、世界の速さを0にして実現する。描画と UI は実秒で動くので、この仕組みのまま扱える。自動の演出（叩き込む段階）は実秒で進める。

**決めること**：固定更新の回数（demo は1秒に120回）。なぞり中の高速移動で、1回の固定更新が大きくなりすぎないか。必要なら、なぞりだけ1回の更新の中で細かく分けて処理する。

## 6. 大量の敵・弾・ドロップ

**仕様から来る条件**：敵1300体前後、経験値の結晶は最大600個、機雷は最大250個、ほかに弾と破片がある。スマホでも 60fps。

**案**

- 敵1体ごとにノードを作らない。種類ごとの配列（位置、速度、HP、装甲、半径、状態、タイマーなど）でまとめて持つ。`PackedFloat32Array` などを使い、倒した敵の場所は空きとして再利用する。
- 描画は種類ごとに `MultiMeshInstance2D` でまとめて描く。
- 弾・破片・経験値の結晶・機雷も同じ作りにする。
- 機体とボスは1体ずつなので、ノードにする。ボスは部位（首など）を子として持ち、部位ごとに当たり判定・HP・攻撃を持てるようにする。当たり判定は7章の自前の判定に部位の円を登録する。

**決めること**：敵の個別の行動（ダーターの突進、射撃型の距離の維持など）を、配列のどこにどう持つか。種類ごとに処理を分けるか、共通の状態の仕組みで扱うか。中ボスの行動を、スクリプトで書くか、データ（段階と攻撃の並び）で書くか。

## 7. 当たり判定と空間分割

**仕様から来る条件**：円同士の判定が中心。なぞり中は1回の更新で長い距離を進むので、点の判定では敵をすり抜ける。線の左右45の帯との判定がある。地形（惑星・月）で弾・線・敵が止まる。

**案**

- Godot の物理エンジン（`Area2D`・`RigidBody2D`）は使わず、自前で判定する。数が多く、判定のルールも独自のため。
- 一様な格子で空間を分け、毎回の更新で敵の位置から作り直す。配列は使い回し、更新ごとに新しいオブジェクトを作らない。
- なぞりは「線分と円」の判定で、通った区間を漏れなく調べる。
- 地形は数が少ない（惑星1・月6）ので、格子に入れずに直接調べる。
- フィールドの仕掛けは「領域」として持つ。領域は形（円・帯など）と作用（引き込む、押し流す、触れたら爆発する、縛る）を持ち、自機・描いた線・なぞり中の機体のどれに作用するかをデータで指定する。

**決めること**：フィールドが広くなったとき（仕様書 20.2）、遠くの地形・隕石・仕掛けをどう扱うか。demo の隕石と同じく、画面の近くだけ有効にする方式を全体に広げるか。

## 8. データ構造

### 8.1 定義データ（Resource）

ゲーム中に変わらない値は、`.tres` で持つ。

| クラス | 中身 | 対応する一覧 |
|---|---|---|
| `WeaponDef` | 管理 ID（`W01`）、内部 ID（`forward`）、名前、Lv ごとの値 | [weapons.md](weapons.md) |
| `TraitDef` | 管理 ID（`T01`）、内部 ID、名前、重ね数ごとの値 | [traits.md](traits.md) |
| `EnemyDef` | type ID（`drifter`）、名前、半径、HP、装甲、速度、接触ダメージ、経験値、行動の種類と値 | [enemies.md](enemies.md) |
| `PhaseDef` | 開始と終了、敵の数、敵レベル、補充の速さ、出現の重み、特別なルール | 仕様書 2.3 |
| `MetaUpgradeDef` | 強化の名前、効果、段階ごとの費用 | 仕様書 12 |
| `StageDef` | 星系、フィールドの配置、仕掛けの領域、時間帯の表、中ボス、伝説のモジュール | 仕様書 20〜22 |
| `BossDef` | ボスの名前、部位、HP・装甲、行動 | 仕様書 10・21・23 |
| `LegendaryModuleDef` | 伝説のモジュールの名前と対応する中ボス。能力値は持たない | 仕様書 20.3 |

- 管理 ID は一覧と同じものを使う。一覧からデータへ、データから一覧へ、ID で行き来できるようにする。
- 武器・特性の効果の処理は、発動のきっかけ（一定間隔、高速の接触、なぞった跡、線の終点、撃破、被弾など）ごとに、決まった入口を持つスクリプトにする。

### 8.2 ラン中の状態

| まとまり | 中身 |
|---|---|
| ステージ | モード、ステージ、ボス戦・締めの段階 |
| 時計 | 経過時間、世界の速さ、ヒットストップの残り |
| 機体 | 位置、速度、HP、無敵の残り、勢いの状態 |
| ゲージ | 容量、充填率 |
| 描画 | 描いている線の点の列、上限、開始時の充填率、なぞりの進み具合 |
| 成長 | レベル、経験値、武器ごとの Lv、特性ごとの重ね数、保留中の3択 |
| 敵・弾・ドロップ | 6章の配列 |
| フィールド | 月の位置、隕石の状態（壊したかどうか） |
| 結果 | 撃破数、拾った部品、そのランの最高の速さ |

機体の能力値（最高速度、攻撃力の倍率など）は、基礎値・レベル・特性・ステーションの強化から毎回計算して求める。伝説のモジュールはこの計算に入れない。

ステージをまたいで何を持ち越すか（仕様書 20.2 の未決）が決まったら、ランの状態とステージをまたぐ状態の境目をここに書く。

### 8.3 調整できる数値

- demo の `config.js` にあたる数値を、1つの `GameConfig`（`data/config.tres`）にまとめる。
- ラン中は `Config` が持つ複製を読む。調整パネルは複製だけを書き換え、元のファイルは書き換えない。
- 調整パネルは開発版でだけ使えるようにし、配布版には含めない。

## 9. 入力

**仕様から来る条件**：PC はマウス、スマホはタッチ、キーボードは補助。ゲームパッドは未決。

**案**：機器ごとの入力を、ゲームが使う2つの意図にまとめる。

| 意図 | マウス | タッチ |
|---|---|---|
| 移動：進みたい向きと強さ | カーソルの向き（強さは一定） | 仮想スティックの向きと倒し具合 |
| ペン先：描く位置と押した瞬間 | カーソルの位置とクリック | 指の位置と「描く」ボタン |

- ゲームのシステムは、この2つの意図だけを読む。機器を足すときは、変換するところだけを足す。
- キー操作は Godot の InputMap で定義する。

## 10. 描画と演出

- 描いている線・なぞった跡は、線の点の列から描く。
- 破片・火花・炎などの大量の演出は、6章と同じく配列とまとめた描画で扱う。スマホの性能を考えて、GPU のパーティクルに頼り切らない。
- 画面外の演出は描画だけ省き、位置・寿命の更新は続ける（カメラが動けば同じ状態が見える）。
- 画面の拡大縮小は、表示を伸ばす方式（`canvas_items`）と、縦横比に合わせて広げる設定（`expand`）を使う。カメラのズームは画面の短い辺を基準に計算する（仕様書 13）。

## 11. 保存

- `user://` に保存する。中身は仕様書 12 のとおり（ストーリーの進み具合、伝説のモジュール、ハイスコアを含む）。
- データに版の番号を持たせ、版が変わったら古いデータを新しい形に変換する。読めないデータは壊さずに初期値で始める。
- 設定（音のオン・オフなど）は、セーブとは別のファイルに保存する。

## 12. UI

- すべての UI は `Control` で作り、アンカーとコンテナで画面の大きさに合わせる。座標を決め打ちしない。
- 色と文字の大きさは1つのテーマにまとめる。強化段階の色（仕様書 6）もテーマで管理する。
- 3択・ポーズ・結果は、ラン中の状態を表示するだけにする。選んだ結果は `RunController` に命令として渡す（4.2）。

## 13. 音

- 音の再生口を使い回し、同時に鳴る数に上限を設ける。
- バスを「全体」「効果音」「エンジン音」に分ける。
- 方向性は未決（企画書 16）。

## 14. 検証

- 乱数の種を指定できるようにし、同じランを再現できるようにする。
- 開発版では、fps・敵の数・各システムの処理時間を画面に表示できるようにする。
- 自動テストと長時間の自動プレイは、依頼があるときだけ行う（AGENTS.md）。

## 17. システムの限界
