# Godot 本番の性能調査

依頼者：Tomatoguy1029。対象：Godot 本番 `speed/`。ゲームの数値・挙動の最適化は行っていない。

## 結果

重い場面では、CPUでの全敵更新と、背景の星を毎フレーム作り直す描画処理が大半の時間を占める。敵数約1,290体の固定配置の計測では **33.5 FPS、平均29.9ms／フレーム**。60 FPSの予算16.7msを超えている。

同じ天体配置・敵数・120Hz更新で、**背景層だけを描画しない比較では93.2 FPS、平均10.7ms／フレーム**になった。描画コール数は約448→47回。物理更新1回の全体時間は5.64→5.86msとほぼ同じで、敵の処理が軽くなった結果ではない。背景の描き直しは、比較でも確認できた大きなボトルネックである。この変更は計測プロセス内だけに適用し、ゲーム本体の背景は変更していない。

### 敵が約1,290体いる場面の内訳

| 処理 | 平均ms／表示フレーム | 平均ms／物理更新 |
|---|---:|---:|
| ゲーム更新全体（以下の更新項目を含む） | 20.25 | 5.64 |
| 敵の行動・移動・天体との接触 | 12.02 | 3.35 |
| 出現・補充・再配置の調査 | 3.72 | 1.04 |
| 当たり判定用の格子の再構築 | 3.02 | 0.84 |
| 自機の更新・接触 | 0.72 | 0.20 |
| 背景の星の描画命令生成 | 4.25 | — |
| 敵の描画命令・MultiMesh更新 | 1.98 | — |

ゲーム更新全体は包含時間なので、下の更新項目と合算しない。背景・敵の描画はスクリプトから描画命令を作る経過時間で、GPUの実行時間ではない。

## 原因

### 1. 全敵を毎秒120回更新している

[RunManager](../../speed/scripts/managers/run_manager.gd) は、敵の行動、格子の再構築、出現調査を各物理更新で呼ぶ。[設定](../../speed/project.godot) は120Hzなので、約1,300体に対して毎秒約15万回の行動更新となる。

[EnemyManager.tick](../../speed/scripts/managers/enemy_manager.gd) は全敵について追跡・巡回の三角関数、速度、向き、天体の近傍判定などを計算する。同じ更新で [SpatialGrid.build](../../speed/scripts/common/spatial_grid.gd) が全配列を2回走査し、`head.fill(-1)`で格子を初期化する。さらに `EnemyManager._survey` が全敵を走査して辺ごとの数・種類ごとの数・再配置を調べ、配列と辞書を作り直す。

今回の固定配置では、1物理更新の全体平均5.64ms、最大8.94ms。120Hzの1更新の予算は8.33msで、描画するための余裕も必要になる。FPSが落ちると1表示フレーム内に複数の物理更新が入り、この計測では約3.6回／フレーム、更新全体で20.25msを占めた。背景を外すと約1.3回／フレーム、更新全体7.55ms／フレームになった。物理更新1回のコストが同じでも、表示フレーム内の更新回数が増えるため、背景の4.25msだけを平均フレーム時間から引く計算では改善幅を説明できない。

敵同士を押し分ける総当たりの衝突処理は、このコードにはない。今回計測した重い処理は行動更新・天体との接触・格子・出現調査である。

### 2. 背景の400個の星を、毎フレーム新しい円として描いている

[RenderManager](../../speed/scripts/managers/render_manager.gd) は毎フレーム全層に `queue_redraw()`を呼び、`_draw_background`で400回 `draw_circle()`を呼ぶ。

macOSのスタック採取で、円描画に対応する以下の経路を確認した。

```text
CanvasItem::_redraw_callback
  → RendererCanvasCull::canvas_item_add_ellipse
    → RendererCanvasRenderRD::request_polygon
      → RenderingDevice::index_buffer_create / vertex_buffer_create
        → RenderingDeviceDriverMetal::buffer_create
```

つまり小さな星の再描画に、形状とMetalの描画用バッファを作る作業が繰り返し発生している。固定配置の高密度ケースで背景だけで4.25ms／フレーム、予備計測では約5〜9msだった。描画コール数も全体の約448回のうち、背景を外すと約400回分減る。比較では星400個と背景矩形1個を含む背景層全体の描画命令を止めた。スクリプトから円を描く経過時間に加えて、描画コール・リソース管理の負荷も下がるため、星の計算だけの問題ではない。

### 3. 大量撃破後にはドロップの更新も増える

W03・W04・W08・W17をLv5、T04を5重にして、高速移動を1回実行した予備計測では、平均約505個の経験値が残った。このとき回収処理は2.77ms／フレーム、経験値などの描画命令生成は1.21ms／フレーム、BuildManagerは1.40ms／フレーム。敵の行動・格子・出現調査に、これらが積み上がる。

[PickupManager](../../speed/scripts/managers/pickup_manager.gd) は毎物理更新で各ドロップの距離・吸引・回収を調べ、残す配列を作る。このケースでは平均的な負荷を確認した。個々の連鎖攻撃の最悪瞬間や長時間プレイでの蓄積は未確定。

## 比較計測

| ケース | 配列内の敵等の平均数 | FPS | 平均フレームms | p95フレームms |
|---|---:|---:|---:|---:|
| 序盤・予備計測 | 94 | 57.8 | 17.3 | 25.9 |
| 320秒・予備計測 | 997 | 34.0 | 29.4 | 34.3 |
| 320秒・予備再計測 | 991 | 23.9 | 41.8 | 64.6 |
| 320秒・固定天体配置 | 994 | 60.2 | 16.6 | 18.4 |
| 350秒・固定天体配置 | 1,290 | 33.5 | 29.9 | 34.0 |
| 350秒・同じ固定天体配置、背景層オフ | 1,289 | 93.2 | 10.7 | 15.8 |

配列数には画面付近の隕石も含む。320秒では配置・環境によって60 FPSに達する場合もあり、常に同じ速度まで落ちるという結果ではない。ランごとの天体配置と他プロセスの負荷による変動を認め、予備計測のFPSだけから各設定の改善率を断定しない。

予備計測では背景オフ、1,280×720出力、GPU火花とグローのオフ、60Hz更新も試したが、天体配置を揃える前の計測では比較が不安定だった。最終的に固定配置で背景オフの差を確認した。解像度・火花・グロー・60Hzのそれぞれの改善率は未確定。60Hzのスタック採取を同時に行ったケースは採取による長い停止を含むため、FPS比較から除外した。60Hzへの変更だけで解決するという根拠にはしない。

## GPU側の状況と限界

デフォルトのウィンドウ合わせでは、実際の出力テクスチャは4,682×2,630。論理座標1,280×720に対して、描画するピクセル数は約13.4倍になる。HDR・グロー・画面効果にも関係するため調査候補だが、解像度を下げることによる改善率は今回確定していない。

[GpuSparks](../../speed/scripts/render/gpu_sparks.gd) は、生存する火花がなくても毎フレーム16,384枠を処理し、1,280×720のRGBA16F画像を全消去してから描く。ここも不要な固定負荷の候補。ただし `--gpu-profile`とViewportのGPU時間は今回すべて0を返し、GPU実行時間を取得できなかった。0msで動いているという意味ではなく、GPUを主因と断定する測定値も得られていない。

## 対応の優先順位

1. **背景をまとめて描く。** 星の見た目とパララックスを維持し、再利用できるメッシュ・MultiMeshまたはテクスチャで、400個の円とバッファの毎フレーム生成を減らす。
2. **毎120Hzで必要な処理を分ける。** 高速移動の接触判定の精度を維持しつつ、出現・種類数・辺ごとの調査の頻度と、敵の全件更新・格子再構築のコストを見直す。更新を間引く場合は補間や判定精度の検討が必要で、今回変更していない。
3. **ドロップと連鎖後の負荷を抑える。** 回収用配列の再利用、候補の絞り込みを検討し、経験値量・回収挙動を維持して測り直す。
4. **GPU火花の空稼働と解像度を追加検証する。** CPU側の改善後、GPU計測が取れる環境も含めて寄与を確認する。

## 計測条件・再現

- Godot 4.6.3、macOS 26.4.1、Apple M1、Metal / Forward+、開発用エンジンの実描画。書き出した製品版では未計測。
- ステージ1、永続強化は初期状態をメモリに設定、無敵。通常ケースはW01 Lv1。入力を止め、機体の初期慣性による移動は継続する。開始時計を指定した秒へ進め、6秒準備・通常6秒計測。強化選択は自動選択。
- 固定配置の計測は天体・宇宙塵・隕石もシード1029で作り直す。予備計測は敵の出現乱数だけを固定しており、天体はランダムだった。
- VSync無効の起動引数を使用。実フレーム間隔を計測し、描画コール数のPerformance値は低頻度更新の参考値として扱う。時間計測自体の小さな負荷も含む。
- 別のGodotエディタは起動中だったが、別のゲーム計測プロセスを並行起動していない。端末全体のメモリ使用量・CPU負荷は高く、バックグラウンドアプリを停止していない。
- セーブへ書き込まず、ユーザーのゲーム・設定を変更しない。自動テストスイートは実行していない。

リポジトリのルートから実行する。

```bash
godot --path speed --disable-vsync res://tools/profile_run.tscn -- --time=350
```

比較用の引数は `--background=off`、`--size=1280x720`、`--sparks=off`、`--glow=off`、`--hz=60`、`--attack=on`。これらは計測プロセス内だけに適用する。`--seconds=6`で採取時間を変えられる。`PROFILE_BEGIN`が環境、`PROFILE_RESULT`が測定結果。`play_total`は包含時間で、個別Managerと重複する。

数値の記録は [計測データ](performance-profile-2026-10-09.json)。計測用シーンは [profile_run.tscn](../../speed/tools/profile_run.tscn)。

## 追加：エディタでのスパイクの読み方（2026-10-10）

ユーザー提供のプロファイラー画像では `RunManager._physics_process`39.23ms／8回、`_play_tick`39.21ms／8回、`_run`38.87ms／80回。親・共通ラッパー・lambdaの時間は呼び出し先を含む表示で、これらを足さない。RunManagerの39msは、ゲーム更新8回分の合計（平均約4.9ms／回）である。

| 内包される処理 | 画像の時間（8回合計） | 子の例（親に含まれる） |
|---|---:|---|
| EnemyManager.tick | 23.77ms | `_update`9.09ms、天体の近傍判定など |
| EnemyManager.spawner_tick | 4.72ms | `_survey`4.62ms |
| ProjectileManager.tick | 4.38ms | `_update_hostile`4.33ms |

`RenderManager._draw_background`6.03ms／1回は、上のRunManagerからの更新呼び出しとは別の再描画処理。天体近傍判定 `FieldManager.near_body` は5.40ms／3,721回で、主に敵の更新から呼ばれるためEnemyManagerの時間へ追加して二重計上しない。

このプロジェクトの更新は120Hz（間隔8.33ms）。表示が遅れると、Godotは遅れた更新を次の表示までに複数回実行する。エンジンの既定上限は8回なので、画像はその上限まで実行している状態と読める。60 FPS時の通常2回に対して8回になり、ほぼ同じ1更新の処理が約4倍積み上がる。最初の遅延の原因はこの画像だけでは確定できない。

2枚目の `Physics Time`5.40msは8回の合計ではない。[Godot 4.6の実装](https://github.com/godotengine/godot/blob/4.6/main/main.cpp#L4587) は各物理更新の時間の最大値をデバッガへ送る。`Physics Frame Time`8.33msは120Hzの更新間隔。これらとScript Functionsの合計時間は集計の単位が異なる。

関数自体の負荷を見たいときは、プロファイラーのScopeを `Inclusive`から `Self`へ切り替える。呼び出し先込み／関数自身のみの区別は [Godotのプロファイラー資料](https://docs.godotengine.org/en/4.6/tutorials/scripting/debug/the_profiler.html#scope-of-measurement-and-measurement-windows)、物理更新の上限は [Engineの資料](https://docs.godotengine.org/en/4.6/classes/class_engine.html#class-engine-property-max-physics-steps-per-frame) を参照。
